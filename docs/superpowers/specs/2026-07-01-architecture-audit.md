## duplicated-logic — 37 instance(s)

**Best practice:** Current guidance treats duplication as a spectrum, not a blanket sin. The "Rule of Three" (Fowler/Beck lineage, still the mainstream 2025 framing per understandlegacycode.com and incusdata.com) says wait for a third occurrence before abstracting, because two data points can't prove a real pattern. Kent C. Dodds' AHA principle ("avoid hasty abstractions," kentcdodds.com/blog/aha-programming) and Sandi Metz's maxim "prefer duplication over the wrong abstraction" both warn that a premature or wrong shared abstraction is worse than leaving code duplicated — the correct question is "would both copies change for the same reason?"; if not, the similarity is incidental and shouldn't be merged. However, this pragmatism has a hard carve-out for security- and correctness-critical logic: OWASP-aligned guidance and general security-pattern literature (dev.to/ihonchar "Why Software Design Patterns Matter for Cybersecurity", Wikipedia "Single source of truth") is unambiguous that duplicated validation/guard logic is a named anti-pattern because copies silently drift, and the fix is centralization into one authoritative module regardless of "rule of three" — you patch a security guard once, not N times hoping you found every copy. For Electron specifically, the utilityProcess API (electronjs.org/docs/latest/api/utility-process) runs a full Node.js environment and can `require`/import ordinary modules exactly like the main process, so forking a security guard into a second file for the utility process is unnecessary — it should import the same module.

**Recommendation:** Don't treat this as one homogeneous "37 duplicates" backlog — triage by blast radius using the "same reason to change" test, then fix in three tiers:

1. Security/correctness-critical guards → fix now, no Rule-of-Three deferral. electron/workers/duckdb.utility.ts's forked assertReadOnlySql is the standout: it's already missing 2 of 4 checks from electron/duckdb-service.ts and a stale comment claims parity that no longer exists. Since electron's utilityProcess is a real Node.js environment, delete the fork and have duckdb.utility.ts import the exact same guard module/function used by duckdb-service.ts (extract it to a small shared module if the two files can't import each other directly). Add a regression test that runs the same blocked-SQL fixture list against both call sites so any future drift fails CI immediately — this belongs in your existing security-reviewer gate, not a "nice to have" cleanup.

2. Obvious structural duplication with zero ambiguity → extract now, these already "scream" per AHA. csvEscape (byte-identical pure function), the AbortController-map lifecycle in electron/main.ts (register→signal→delete-in-finally, copy-pasted 3x/2x with a proven local precedent for extraction already sitting in ipc-concurrency.ts's createConcurrencyLimiter), and registerCSVPathDataset/registerParquetPathDataset's ~60-line shared template are all cases where the two call sites unmistakably change for the same reason. Extract a createAbortRegistry() helper and a shared registerDatasetView() helper that takes only the format-specific step (COPY read_csv vs fs.copyFile) as a parameter.

3. The math/algorithm cluster (kMeans, Welch t-test/logGamma/incompleteBeta, Holt-Winters, z-score/IQR anomaly detection, Pearson correlation, rule-based "insight" generators) is the most consequential category: this is duplication that has already passed the Rule-of-Three threshold (4-6 independent reimplementations each) and has visibly drifted in quality (hardcoded z-critical table vs. exact bisection; sklearn/Pyodide path with no cross-validation against the JS z/IQR/MAD/GESD paths). This is not a "wait and see if it's a real pattern" situation — it already is one, and it's user-visible (the app gives different-quality forecasts depending on which screen you're on). Consolidate onto the already-correct precedent in this repo: src/platform/viz/stats-core.ts + src/platform/viz/analysis-client.ts's getAnalysisProxy(), which src/features/ai-analysis/worker/kernels.ts already uses correctly. Migrate deep-analytics, forecast-intelligence, telecom/lib/insights.ts, and platform/ai/insights.ts to import from that canonical module instead of reimplementing; unify the four/five divergent Insight/AgentInsight type shapes into one. Given check-architecture.mjs already enforces @/lib retirement and moved-UI rules via dependency-cruiser, add a matching rule (or a simple grep-based CI check) that flags new top-level definitions of known canonical names (kMeans, holtWinters, logGamma, incompleteBeta, pearsonCorr) outside the canonical module, so this cluster doesn't regrow.

For the persisted-store duplication (activity-store.ts etc. hand-rolling migrate/partialize instead of using durablePersist), this is the inverse problem — the correct abstraction already exists and is proven (3 stores use it) but wasn't adopted uniformly. Don't design a new abstraction; just migrate the remaining 6 stores to the existing durablePersist/makeDeepMergeMigrate/pickKeys helper and enforce adoption going forward via the same architecture-check mechanism.

**Verification note:** I verified the review's flagship security claim by reading the actual code, and it holds up factually — this is not a case of legitimate "prefer duplication" pragmatism.

electron/duckdb-service.ts:assertReadOnlySql (lines 592-650) has 4 safety checks after the read-only-prefix allowlist: blocked statement keywords, blocked file/IO functions (read_csv/read_parquet/getenv/etc.), a blocked "FROM/JOIN 'string-literal'" replacement-scan vector, and a blocked SET-config check.

electron/workers/duckdb.utility.ts:assertReadOnlySql (lines 73-111) has only 2 of those 4: keywords and SET-config. It is genuinely missing the blocked-functions and from-string-literal checks — confirmed by direct diff, not review-narrative alone.

The file's own comment claims this "mirrors the in-main textual guard" and that "the broker only routes already-validated SQL" — both are false. I traced the actual call path: electron/main.ts's duckdb:runReadOnlyQuery handler only passes the SQL through `SqlSchema = z.string().min(1).max(MAX_SQL_CHARS)` (electron/ipc-validation.ts:38) before routing to the utility broker when DN_DUCKDB_UTILITY=1 — that's a length check, not `assertReadOnlySql`. The full 4-check guard is only invoked on the in-main fallback path. So the utility process's weaker 2-check guard is the only SQL-safety gate on that path, contradicting its own "already-validated" comment.

This isn't fully compensated by the filesystem `allowed_directories` sandbox either: that sandbox stops file-path exfiltration but does nothing about `getenv()` calls (an env-var read, not a file read), which is one of the specific functions the main guard blocks and the utility guard doesn't. Since utilityProcess.fork() here (electron/workers/duckdb-utility-broker.ts) doesn't pass an explicit restricted `env`, this is a real (if currently narrow/behind an off-by-default DN_DUCKDB_UTILITY=1 flag) drift, not a false positive.

I also confirmed there is no shared regression test enforcing parity — tests/electron/sql-guard.test.ts exists only for the separate assertSafeFilterFragment/electron/sql-guard.ts function, not for either assertReadOnlySql implementation. And I confirmed the extraction is actually feasible and matches an existing pattern already used in this repo: electron/sql-guard.ts is exactly this kind of pure, dependency-free, already-extracted-and-tested guard module (electron/duckdb-service.ts imports `electron`'s `app`, which the utility process correctly avoids — so a small shared pure module, not a direct cross-import, is the right fix, precisely as the review recommended).

I additionally spot-checked the lower-severity structural claim (src/core/stores/activity-store.ts hand-rolling version/migrate/partialize instead of the existing durablePersist/pickKeys/makeDeepMergeMigrate helpers in src/platform/storage/persist-helpers.ts) and confirmed it too: activity-store.ts defines its own `version: 1`, `migrate: (persisted, _version) => {...}`, `partialize: (s) => ({ events: s.events })` block rather than spreading `durablePersist({...})`, even though that helper exists and is designed for exactly this.

Given the security-critical guard duplication is verified as real, drifted, and inadequately tested — and the review's proposed fix (extract to a shared pure module, per the sql-guard.ts precedent, plus a shared fixture-based regression test) is both correct and low-risk — I confirm this as a genuine, worth-fixing issue, at least for the security-tier item and the sampled structural item. The review's tiered/triaged framing (fix security guards now regardless of Rule-of-Three, extract obvious zero-ambiguity duplication, treat the math/stats cluster as already past the Rule-of-Three threshold) is methodologically sound and consistent with what I verified in the code, so I'm not flagging the overall approach as premature-abstraction risk.

## oversized-file — 15 instance(s)

**Best practice:** Current (2025-2026) guidance converges on "many small cohesive files" as the antidote to God Objects/God Files: split by responsibility, not by type. For React/Next.js, official Next.js docs and community guides (Robin Wieruch, Vercel) recommend colocation — a file lives as close as possible to where it's used, moving up a level only when shared — plus one exported component per file, with large screens broken into a thin container (route/screen) that composes small presentational sub-components, and business/data logic pulled out into custom hooks (the "container-as-hook" evolution of the classic container/presentational pattern) rather than living inline in a 1000+ line render function. State libraries like Zustand formalize the same idea via the official "slices pattern": each domain slice is its own file/creator function, composed into one store via spread, with middleware (devtools/persist) applied only at the composition point — this maps directly onto this repo's ~20-store Zustand setup and 13+ Dexie tables in app-db.ts. On the Electron/Node side, the general anti-pattern is the "God Object/God File" (Wikipedia, TheServerSide, InfoWorld): a module accreting unrelated responsibilities over time by always being the path of least resistance to add "just one more handler." The fix is decomposition by responsibility with a stable public interface (extract-class/extract-module refactoring, SRP), and for Electron specifically the community pattern (LogRocket, NestJS-inspired "electronest") is to register IPC handlers per-domain in separate files/modules (e.g. settings.ipc.ts, fs.ipc.ts, duckdb.ipc.ts) that are composed in main.ts rather than one file hosting every ipcMain.handle call plus window lifecycle and server bootstrap.

**Recommendation:** Apply the same decomposition move to all 15 instances, keyed to the concern boundaries already identified in each file, and do it incrementally (extract-and-verify, not a rewrite):

1. Electron main-process files (main.ts, duckdb-service.ts): split by IPC domain into sibling files under electron/ipc/ (settings.ipc.ts, fs.ipc.ts, duckdb.ipc.ts, voice.ipc.ts, llama.ipc.ts, models.ipc.ts, collabHub.ipc.ts), each exporting a `registerXHandlers(ipcMain, deps)` function, composed in main.ts; main.ts keeps only window lifecycle + Next.js bootstrap + handler registration calls. ## oversized-function — 13 instance(s)

**Best practice:** Current tooling and style guidance converge on the same operational rule the project's own AGENTS.md already states: keep functions small and single-purpose, extract by "what it does" not by arbitrary line-splitting. ESLint's `max-lines-per-function` defaults to 50 lines and SonarSource's cognitive-complexity rule (used via eslint-plugin-sonarjs/SonarQube) defaults to a threshold of 15, both used as CI gates in modern TS repos; Martin Fowler's guidance is even stricter — extract a fragment into a named function the moment you have to pause and figure out "what" it does, favoring many small, well-named functions over comments. For React specifically, 2025-2026 guidance (rtcamp's component-architecture handbook, Alex Kondov's "Common Sense Refactoring of a Messy React Component", CodeScene's custom-hooks refactoring writeup) says a component mixing data-fetching + derived-state + multi-branch rendering is doing too many jobs — pull side-effecting/stateful logic into named custom hooks (`useX`) and pull large mutually-exclusive render branches (tabs, panels) into their own components, composing the parent from them. For Electron main-process code and for hand-rolled animation/canvas engines, the applicable pattern is Humble Object / Functional Core–Imperative Shell (Martin Fowler's bliki, xUnitPatterns.com): isolate the framework-bound, hard-to-test "shell" (BrowserWindow wiring, the requestAnimationFrame loop, canvas draw calls) into a thin function, and move the actual decision/computation logic (retry backoff policy, layout/particle simulation, warm-session prompt fallback logic) into small, pure, independently testable functions or modules that the shell merely calls.

## unclear-boundary — 8 instance(s)

**Best practice:** Current guidance converges on a few concrete rules for this exact failure mode (state/logic ownership split across multiple places with no enforced boundary). For client state, the Zustand team's own docs recommend one bound store composed of domain "slices" (spread-merged with TypeScript slice typing) rather than several independently-created and independently-persisted stores for overlapping concepts — cross-slice reads happen via selectors on the single store, not via manual fan-out writes to N stores. For undo/redo and other reversible operations, the standard fix for duplicated mirror-image switch statements is the Command pattern: each action type registers a `{do, undo}` pair in one table, so a generic executor/undo-stack does the branching instead of two hand-written switches that can drift apart. For "screen owns IO+business logic+persistence" components, React's own docs and multiple 2025 architecture write-ups (profy.dev, felixgerschau.com) prescribe pulling that logic into custom hooks/services (thin presentation layer, hook layer for orchestration, pure functions for business rules), exactly the pattern this codebase already uses inconsistently in `parsed-data`. ## dead-or-unused-code — 7 instance(s)

**Best practice:** Current best practice (2025-2026) for JS/TS projects treats dead code as a cross-file reachability problem that single-file linters (ESLint no-unused-vars) cannot see, and recommends a dedicated reachability tool — Knip is the de facto standard, tracing imports from declared entry points (pages, workers, CLI scripts) to flag files, exports, types, and dependencies with zero reachable importers (https://knip.dev/, https://github.com/webpro-nl/knip). The consensus operational guidance is: wire the tool into CI/pre-push as a **blocking** gate rather than an advisory report — "a better approach is catching it before git push ever completes... every git push runs knip first... the push is blocked until you clean them up" (https://recca0120.github.io/en/2026/05/02/knip-dead-code-detector/) — starting from warnings and graduating to hard failures as the codebase is brought under control (https://axify.io/blog/dead-code, https://pensero.ai/blog/dead-code). A well-documented gotcha of reachability tools, including Knip itself, is that they treat "imported by a test file" as "used," so production-dead code that still has a leftover unit test is invisible to a default run; Knip's own docs prescribe `--production` mode (and NOT hand-rolled ignore/project-glob excludes) specifically to strip test-only entry points and surface this class of false negative (https://knip.dev/features/production-mode, https://knip.dev/guides/configuring-project-files).

I verified this against the actual repo rather than relying on the survey text alone. `knip.json` and `check:deadcode` (`knip`) already exist and, run live, correctly flag 48 unused files and 348 unused exports — including the exact `saveSessionState`/`loadSessionState`/`SessionState` dead code the survey cited in `src/platform/storage/app-db.ts`. So the detection tooling is not the gap. The gap is enforcement: `package.json:43` runs `quality` as `... && (pnpm run check:deadcode || true) && ...`, and `.github/workflows/quality.yml:97-100` runs the same step with `continue-on-error: true` under the explicit comment "Advisory: knip findings should not block the PR gate." ## inconsistent-pattern — 6 instance(s)

**Best practice:** Current guidance (Zustand docs, pmndrs GitHub discussions, and general architecture-consistency literature) converges on two points relevant to this "inconsistent-pattern" category. First, Zustand's persist middleware is explicit that `version` + `migrate` (with `persistedState: unknown` typing and an explicit switch/case per version) is the only safe way to evolve persisted shape — if `version` is omitted it silently defaults to `0`, and any future bump without a `migrate` fallback returns raw old state as the new state, which is exactly the "silent schema-mismatch data loss" risk already documented in this repo's own `persist-helpers.ts`. Second, for the broader pattern (selector conventions, component decomposition, modal primitives, duplicated IPC bridge types), the industry consensus is that convention documentation alone doesn't survive team/agent-driven growth — you need an automated "architecture fitness function" (Neal Ford's term, popularized via *Building Evolutionary Architectures*) that runs in CI: dependency-cruiser or `eslint-plugin-boundaries`/custom ESLint rules to make import/pattern rules executable rather than advisory, plus dead-code/duplication scanners (Knip) to catch abandoned canonical components like the unused shared `Dialog`.

**Recommendation:** Treat this as one root cause — undocumented conventions with no automated enforcement — rather than six separate fixes, and close it in two passes that reuse tooling already in this repo (per project memory: dependency-cruiser via `check:architecture`, Knip, Biome) instead of adding new dependencies:

## state-management-sprawl — 3 instance(s) _(plausible, not fully confirmed)_

**Best practice:** Current guidance across React and Zustand converges on cohesion-by-domain over cohesion-by-mechanism. Kent C. Dodds' "state colocation" principle says state should live as close as possible to where it's used and be split by concern — components with long useState lists are a signal to extract each cohesive concern into its own custom hook (or store), not to keep piling more useState calls into one component; it also separates "server cache" state from "UI state" since they have different lifecycles. For Zustand specifically, the official docs and pmndrs maintainer discussions recommend the "slices pattern": each independent domain gets its own slice function (or, if the domains are truly unrelated/independently consumed, its own separate store), slices live in their own files, cross-cutting actions get a dedicated combining slice, and middleware (persist/devtools) wraps the composed store rather than individual slices. The community consensus (2025) is "one store split into per-domain slices for coordination, multiple stores when domains are independent and you want to avoid unrelated re-renders" — the deciding factor is whether a selector in one domain re-renders on unrelated domain updates, which is exactly the desktop-store.ts problem (windows dragging re-renders anything subscribed to `wallpaper`/`glassPalette` unless callers use narrow selectors everywhere).

**Recommendation:** Apply the slices-pattern split that the project's own sibling features (channel-monitor, data-formulator, dashboard-home, ai-briefing, collab-hub) already use, rather than inventing a new pattern:

1. `desktop-store.ts` (594 lines, 6 domains, ~35 actions): split into per-domain slice files under `src/features/desktop/store/slices/` — `windows-slice.ts` (window mgmt/snap/resize/tab-grouping), `recycle-bin-slice.ts`, `snapshots-slice.ts`, `widgets-slice.ts`, `workspaces-slice.ts`, `shell-preferences-slice.ts` (wallpaper/glassPalette/launcher/spotlight/iconPositions/dockProgress). Compose them with the standard `create<DesktopState>()((...a) => ({...createWindowsSlice(...a), ...createRecycleBinSlice(...a), ...}))` pattern, keep `persist` wrapped around the composed store only (not per-slice), and add a `desktop-cross-slice.ts` only for the few actions that genuinely need to touch two domains at once (e.g. closing a window that also updates dock progress). This directly fixes the unnecessary-re-render problem: a component that only reads `windows` should never re-render because `wallpaper` changed.

2. `DataBrowserScreen.tsx` (50 `useState` hooks): give data-browser a `store/` directory like its siblings and extract the useState clusters into cohesive custom hooks or a Zustand store, grouped by the same domains already visible in the state names — `useDataBrowserQuery` (dbReady/dbLoading/totalRows/columns/rows/queryLoading), `useDataBrowserFilters` (filterGroup/savedFilterGroups/sorts), `useDataBrowserSelection` (selectedRows/editedCells), `useDataBrowserColumns` (colPanelOpen/columnStats/resizingCol/starredKeys). Follow Kent C. Dodds' colocation rule: keep genuinely local/ephemeral UI state (e.g. a single popover's open flag) as component-local useState, and only promote state to the store/custom-hook layer when it's shared across the component tree or has real cross-cutting logic — don't over-centralize everything into one giant store either.

3. General rule to apply to all three sprawl instances: a store/interface should map to one bounded domain; if you can't describe what the store owns in one sentence without "and," split it. Use narrow Zustand selectors everywhere downstream so the split actually pays off in reduced re-renders, not just file organization.

## deep-nesting — 2 instance(s) _(plausible, not fully confirmed)_

**Best practice:** Current React/TypeScript guidance (react.dev's "Thinking in React" and widely-cited composition writeups like developerway.com) converges on two rules for this exact smell: (1) any JSX block that is complex enough to reason about on its own — a filter-rule row, a per-step config form — should be extracted into its own component rather than left inline, because inline complexity is what produces runaway indentation, poor testability, and unnecessary re-renders of unrelated siblings; and (2) long `type === X && (...)` or switch-on-discriminant chains inside JSX should be replaced by dispatching on a lookup table/registry keyed by the discriminant, mirroring how TypeScript discriminated unions are meant to be consumed. Since data-navigator's `StepType` is already a proper discriminated union with sibling lookup tables (`STEP_DEFAULTS`, `STEP_COLORS`, `STEP_ICONS`), the idiomatic fix is a `Record<StepType, ConfigFormComponent>` registry so the render tree does one `StepConfig[activeStep.type]` lookup instead of 10 branches, consistent with the "strategy/registry over switch" pattern favored for discriminated unions in 2025-2026 TS guidance. The same principle applies to the filter-rule editor: extract a `FilterRuleRow` (and nested `FilterRuleValueInput`) component that owns its own `onValueChange`/`produce()` mutation logic, so each `rules.map(...)` iteration renders a named component instead of 12 levels of anonymous inline JSX.

**Recommendation:** For both files, apply the same two-step refactor rather than treating them as one-off JSX cleanups:

1. **DataTransformScreen.tsx (lines 1082-1259):** Extract a `StepConfigForm` component per step type (e.g. `FilterStepConfig`, `SelectStepConfig`, `AggregateStepConfig`, `JoinStepConfig`, ...), each taking `{ step, onUpdateConfig }`. Build a `STEP_CONFIG_FORMS: Record<StepType, React.ComponentType<StepConfigFormProps>>` registry next to the existing `STEP_DEFAULTS`/`STEP_COLORS`/`STEP_ICONS` tables (same file, ~line 119), and replace the 10-branch `activeStep.type === X && (...)` chain with a single `const ConfigForm = STEP_CONFIG_FORMS[activeStep.type]; <ConfigForm step={activeStep} onUpdateConfig={updateStepConfig} />`. This collapses ~38-space indentation down to a single dispatch line and gives each step type its own small, independently testable/typed component (TypeScript can narrow `step.config` per type since `StepType` is already a discriminated union).

2. **DataBrowserScreen.tsx (lines 1721-1878):** Extract the per-rule JSX into a `FilterRuleRow` component (`{ rule, index, onChange, onRemove }`) that internalizes the `Select`/`SelectContent`/operator-branch/`produce()` logic currently inlined inside `rules.map(...)`. Where the rule editor branches on `rule.operator` (e.g. the `between` case at line 1863), extract a `FilterRuleValueInput` subcomponent that switches on the operator internally, again via a small lookup/branch localized to one component instead of nested inside the outer render tree. This turns the outer render into `rules.map((rule, i) => <FilterRuleRow key={rule.id} rule={rule} index={i} onChange={...} onRemove={...} />)`, dropping nesting from 12 levels to roughly 4-5 in the parent and isolating the remaining branching inside the new leaf component.

Neither fix requires new dependencies — both reuse the codebase's existing conventions (discriminated `StepType`/lookup-table style already used for `STEP_DEFAULTS`/`STEP_COLORS`, and existing `produce()`/immer update patterns), so this is a pure extraction/decomposition change, not an architectural addition.

**Verification note:** Checked both flagged ranges directly against the source.

Facts that hold up:
- Line numbers are accurate. DataTransformScreen.tsx:1082-1259 is exactly the `activeStep.type === X && (...)` chain (10 branches); DataBrowserScreen.tsx:1721-1878 is exactly the `filterGroup.rules.map(...)` filter-row JSX, and the `rule.operator === "between"` branch really is at line 1863.
- STEP_DEFAULTS (line 119), STEP_COLORS/STEP_ICONS (StepCard.tsx, both typed as `Record<StepType, ...>`) genuinely exist, so a `Record<StepType, ComponentType>` registry would be consistent with an established codebase convention, not a novel abstraction.
- Both files are far over the project's own 800-line guideline (DataTransformScreen.tsx = 1619 lines, DataBrowserScreen.tsx = 3030 lines), which independently supports decomposition.
- DataBrowserScreen's filter row has a real DRY smell: four separate `onValueChange`/`onChange` handlers each doing `setFilterGroup(prev => produce(prev, draft => { const r = draft.rules.find(x => x.id === rule.id); if (r) r.<field> = v }))` — near-identical boilerplate repeated per field, which extracting into `FilterRuleRow`/an `updateRule` helper would genuinely clean up.

Reasons to be skeptical of the framing as stated:
- Measuring actual indentation, the "19 levels / 38 spaces" figure for DataTransformScreen is real only at the deepest point (line 1193, inside the `join` branch's `Select > SelectContent > .filter().map() > SelectItem`), and roughly 11 of those levels already exist before any step-type branch starts (root div → header/body split → Tabs → TabsContent → ternary-else div → Card → CardContent). The 10 `type === X &&` branches are siblings, not nested inside each other — each adds only 1-3 extra levels on top of that baseline, not a cascading nesting problem. Extracting into a registry component would mostly relocate that baseline nesting into a new file (where it resets to a fresh, shallow indentation), not eliminate the underlying Select/SelectContent/SelectItem composition depth, which is intrinsic to using shadcn's Select primitive with a mapped list and would recur inside the extracted component too. So "reduces 19 levels to a single dispatch line" somewhat overstates what the refactor actually achieves — it's a real readability/organization win (smaller functions, per-type typing/testability, less scrolling), but not a fix for "runaway nesting" in the classic control-flow sense.
- Several of the 10 branches are trivially small (1-2 `ConfigField` calls already using a shared component), so full per-type component extraction for all 10 is partly YAGNI; a more proportionate fix might extract only the two genuinely complex branches (`sort`, `join`) that use inline `Select`.
- No project lint rule (biome.json) enforces a nesting-depth or complexity threshold here — the "4-level max" is the user's personal global guideline, not something already enforced/violated by CI in this repo.
- The current state postdates a large, deliberate June 2026 refactor commit ("Refactor code structure for improved readability and maintainability") that rewrote ~1800/1600 lines of exactly these two files and still left this structure — weak signal it wasn't accidental, though not proof it was a considered trade-off.

Net: this is a legitimate, low-risk maintainability cleanup opportunity (especially the DataBrowserScreen filter-row DRY violation), grounded in real, verifiable code and consistent with existing registry conventions — but the "deep nesting / architecture violation" framing partly conflates unavoidable structural JSX composition (Card/Select library nesting) with actual runaway control-flow nesting, and overstates how much the DataTransformScreen refactor would truly reduce structural depth versus just relocate it. It's real and worth doing, not a false alarm, but not a critical/blocking issue either.
