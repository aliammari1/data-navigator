# Tech Radar Brief — Offline-first in-browser/on-device analytical data engine: DuckDB tuning, Arrow, Parquet, OPFS, streaming & columnar transforms for data-navigator (Next.js 16 + Electron, medium-end PC)

## Key findings

- data-navigator ALREADY runs the optimal offline engine: native DuckDB via @duckdb/node-api (Neo) in the Electron main process, converting CSV to a managed Parquet cache and exposing datasets as views. This native path is 5-50x faster than duckdb-wasm, has no SharedArrayBuffer/COOP-COEP constraints, no 4GB WASM memory ceiling, and uses real OS threads/SIMD on the medium-end target. Keep this as the primary engine; do NOT migrate the desktop path to duckdb-wasm.
- Benchmark consensus (timlrx, VLDB Kohn et al., John Guerra study): on analytical workloads DuckDB beats pure-JS dataframe libs (Arquero/Danfo) by 10-100x and scales far better with data size. SQLite-WASM wins only on indexed point lookups / transactional row updates. For an analytical app, SQL-on-columnar (DuckDB) is the right default; Arquero is a lightweight complement, not a replacement.
- Parquet + Arrow are the load-time superpower: loading from Parquet/SQLite at the memory-buffer level is >2x faster than CSV parsing, and DuckDB returns results as Apache Arrow for zero-copy hand-off to charts/tables. The app's existing 'CSV -> managed Parquet cache' design is exactly the recommended pattern - it pays the CSV parse cost once and makes every subsequent query fast and seekable.
- duckdb-wasm (only needed if a browser-only fallback is ever required) ships 3 bundles - MVP (single-thread), EH (exception handling), COI (multi-thread via SharedArrayBuffer). The fast COI bundle REQUIRES cross-origin isolation headers (COOP: same-origin + COEP: require-corp). On the medium-end/no-WebGPU target this is the key tuning lever, with selectBundle() doing graceful capability-based fallback. Bundle is ~3.5MB so it must be lazy-loaded in a worker, never on the main thread.
- Push compute to SQL and stream: prefer LIMIT/aggregate/window queries over pulling raw rows; the renderer should request dataset-level aggregates, not full tables. Use DuckDB's streaming/row-readers (Neo's chunked readers, or duckdb-wasm send()/Arrow IPC streams) plus UI virtualization so big results never materialize fully on the main thread.
- For columnar transforms that don't need a SQL round-trip, Arquero (BSD-3, ~1.5k stars, active May 2025, 105kB) is the mature pick and now sits on @uwdata/flechette - a faster, zero-dependency Arrow reader (~14kB gzip vs ~43kB for apache-arrow). Flechette is small-but-niche (~100 stars); justified because it's maintained by the same Arquero/UW lab and is a drop-in lightweight Arrow layer. Keep apache-arrow (11k stars, Apache-2.0, healthy) as the interop/type backbone.
- Big-CSV ingestion: never read a multi-hundred-MB File through IPC or into a JS string. The app already does the right thing (path-based registration handled in Electron main where DuckDB's vectorized read_csv / COPY streams directly off disk). For any browser-only path, use duckdb-wasm registerFileHandle + insertCSVFromPath / read_csv on an OPFS file rather than buffering the whole file.
- Recommended dependency set is already 90% in package.json (DuckDB Neo, arquero, comlink, apache-arrow transitively). The only additive considerations are optional: @uwdata/flechette (lighter Arrow) and, ONLY if a pure-browser fallback engine is required, @duckdb/duckdb-wasm. comlink (GoogleChromeLabs, ~11k stars, Apache-2.0, ~1.1kB) is the right worker-RPC glue and is already a dependency.

# Offline-First Analytical Data Engine — Tech Radar Brief\n## data-navigator (Next.js 16 + Electron, fully on-device, medium-end PC target)\n\n> Date: 2026-06-11. All recommendations satisfy the hard constraints: 100% offline at runtime, medium-end PC (4-8 cores, 8-16GB RAM, WebGPU often absent), and mature/permissive dependencies only.\n\n---\n\n## 0. TL;DR / Verdict\n\n**You are already on the recommended architecture.** `package.json` and `src/platform/duckdb/*` show the app runs **native DuckDB in the Electron main process** via `@duckdb/node-api` (the \"Neo\" client, v1.5.3-r.3), converting **CSV → a managed Parquet cache**, exposing each dataset as a **view**, and returning previews/aggregates to the renderer over IPC. Arquero (^8.0.3) and Comlink (^4.4.2) are already present for client-side columnar transforms and worker offloading.\n\nThis is the *fastest, most robust* offline option for a desktop app. The job now is **tuning and disciplined query design**, not a re-platform:\n\n1. **Keep native DuckDB as the primary engine.** Do not migrate the desktop hot path to `duckdb-wasm` — native is 5-50x faster, has no 4GB WASM cap, no COOP/COEP requirement, and uses real OS threads/SIMD.\n2. **Push compute into SQL.** Renderer asks for aggregates/LIMITs/windows, never raw full tables.\n3. **Stream + virtualize** results; keep Arrow zero-copy from engine → chart/table.\n4. **Treat `duckdb-wasm` / `hyparquet` / `parquet-wasm` as *optional fallbacks*** only if you ever ship a non-Electron browser build.\n5. Optional footprint win: adopt **`@uwdata/flechette`** as a lighter Arrow layer.\n\n---\n\n## 1. Current architecture (what the code shows)\n\nFrom the repository:\n\n- `electron/duckdb-service.ts` + `src/platform/duckdb/shared-duckdb.ts` — DuckDB lives in **Electron main**; the renderer talks only to **dataset-level IPC** (`registerCSVPathDataset`, `registerParquetPathDataset`, `previewDataset`, `summarizeDataset`, `exportDataset`). The renderer explicitly **does not** run raw SQL, manage tables, or push large CSV buffers through IPC. This is the correct security + performance boundary.\n- `src/platform/duckdb/upload-to-duckdb.ts` — ingestion is **path-based**: Electron hands DuckDB a real filesystem path, DuckDB streams the file. CSV/TSV/TXT → managed Parquet cache; Parquet copied into cache. Renderer receives a descriptor + preview rows.\n- `src/core/queries/duckdb.ts` — React Query wrappers (`useDuckDBQuery`, `useTableSchema`, `useTablePreview`, `useTableRowCount`) with sane `staleTime`/`gcTime`. `runReadOnlyQuery` is SQL-only; `params` are cache-key only (a real bound-parameter API is a noted TODO — see §9 security).\n\n**Why this is the right baseline:** native DuckDB beats every in-browser option on the metrics that matter for an analytical desktop app, and the CSV→Parquet cache is the single highest-leverage ingestion decision (see §4).\n\n---\n\n## 2. Engine landscape & honest comparison\n\n### Benchmark evidence (2022-2025, multiple independent sources)\n\nFrom timlrx's *\"The Best In-Browser Data Processing Framework is SQL\"* (1M Bandcamp rows, 24 fields; Chrome 116 i7-1165G7 / Firefox 117 M2):\n\n| Workload | DuckDB | SQLite (indexed) | Arquero |\n|---|---|---|---|\n| Top-level aggregation | **0.014–0.007 ms** | 0.103–0.074 ms | 0.067–0.051 ms |\n| Daily grouping | 0.163 ms | **0.005–0.001 ms** (index) | 1.05–0.634 ms |\n| Window (top-5 by type) | **0.114 ms** | 0.165 ms | (Danfo 3.4 ms) |\n| 1,000 indexed point reads | 1.048 ms | **0.054–0.020 ms** | — |\n| 1,000 row updates | 0.588 ms | **0.062–0.034 ms** | — |\n\nThe VLDB paper (*DuckDB-Wasm: Fast Analytical Processing for the Web*, Kohn et al.) reports **DuckDB-Wasm outperforms Arquero/Lovefield by 10-100x across all scale factors**, and the gap *widens* as data grows. John Guerra's student benchmark reaches the same conclusion vs VanillaJS/Arquero.\n\n**Bundle sizes (from the same sources):** Arquero **105 kB**, SQLite-WASM **~400 kB**, DuckDB-WASM **~3.5 MB**.\n\n### How to read this for data-navigator\n\n- **Analytical (group-by, window, aggregate, join) → DuckDB.** This is your dominant workload. Native DuckDB is even faster than the WASM numbers above (no WASM overhead, real threads).\n- **Transactional point lookups / row mutations → SQLite shines**, but that's not an analytical-dashboard pattern. You already have `better-sqlite3` + `sqlite-vec` for app/metadata/vector storage — keep that split (SQLite for app state & embeddings, DuckDB for analytics).\n- **Lightweight client-side reshaping without a SQL round-trip → Arquero.** Good for a few-thousand-row pivot/derive in the renderer; do NOT use it for multi-hundred-MB scans (it scales worse and runs on the main thread unless workerized).\n\n---\n\n## 3. Native DuckDB (Neo) — tuning the primary engine\n\n`@duckdb/node-api` is the modern replacement for the old callback `duckdb` package (which stops at DuckDB 1.4.x, ~Fall 2025; Neo is the 1.5.x+ path). It wraps released DuckDB binaries (no source rebuild), is Promise-native, TypeScript-first, lossless across all DuckDB types, and exposes chunked/column-major or row-major readers.\n\n### Tuning levers (set in the Electron main service)\n\n```ts\n// electron/duckdb-service.ts (sketch)\nimport { DuckDBInstance } from '@duckdb/node-api';\n\nconst instance = await DuckDBInstance.create(dbPath, {\n  threads: String(Math.max(2, Math.min(navHwConcurrency, 6))), // leave cores for UI/Electron\n  memory_limit: '4GB',          // cap so a huge scan can't OOM a 8GB machine\n  temp_directory: tmpSpillDir,   // allow out-of-core spill for big joins/sorts\n  max_temp_directory_size: '20GB',\n});\nawait instance.connect().then(c => c.run(\"PRAGMA enable_progress_bar; PRAGMA enable_object_cache;\"));\n```\n\nKey knobs for a medium-end PC:\n- **`threads`**: don't grab all cores; cap at ~`cores-2` (e.g. 4-6) so the renderer/compositor stay responsive.\n- **`memory_limit`**: explicit cap (e.g. 4GB on a 8GB box). DuckDB is out-of-core: with `temp_directory` set, sorts/joins/aggregations spill to disk instead of crashing.\n- **`enable_object_cache`**: caches Parquet metadata/footers across queries — big win when the same cached Parquet files are queried repeatedly.\n- **Read-only connections for queries**: you already separate read vs write (status exposes `readConnections`); keep query connections read-only so DuckDB can parallelize freely.\n\n### Streaming results (don't materialize everything)\n\nNeo exposes incremental readers — read only the rows the UI needs:\n\n```ts\nconst reader = await connection.runAndReadUntil(sql, /*targetRowCount*/ 1000);\nreader.getRowObjects(); // first page only; call readUntil(moreRows) on scroll\n```\n\nFor exports/large transfers, prefer **Arrow IPC**: `connection.run(sql)` → fetch as Arrow chunks and stream them, instead of JSON-stringifying millions of rows across IPC.\n\n### Migration note (old `duckdb` → Neo)\nIf any legacy `duckdb` (callback) usage remains: replace `db.all(cb)` with `await connection.run(sql)`; replace manual prepared-statement callbacks with `await connection.prepare(sql)` then `.bind(...)`/`.run()`. Neo has **native parameter binding** — adopt it to close the SQL-injection gap noted in §9.\n\n---\n\n## 4. Parquet & Arrow — the load-time and interop story\n\n### Parquet cache = correct (keep it)\nThe app converts CSV → managed Parquet once. Evidence: loading from Parquet/SQLite at the memory-buffer level is **>2× faster than CSV parsing**, and Parquet is columnar + compressed (zstd) so:\n- Only the **columns a query touches** are read (projection pushdown).\n- **Predicate pushdown** + row-group statistics skip irrelevant data.\n- Re-querying a dataset never re-parses CSV.\n\nTuning the cache write:\n```sql\nCOPY (SELECT * FROM read_csv(?, AUTO_DETECT=true, SAMPLE_SIZE=20000))\nTO 'cache/ds.parquet' (FORMAT PARQUET, COMPRESSION ZSTD, ROW_GROUP_SIZE 122880);\n```\n- **ZSTD** compression: best size/speed for local disk.\n- **ROW_GROUP_SIZE** ~100-120k rows: good granularity for pushdown without tiny-group overhead.\n- Consider partitioning very large datasets by a common filter column (`PARTITION_BY`) so dashboards that always filter on, e.g., `period` skip whole files.\n\n### Arrow = the zero-copy bridge\nDuckDB returns results as **Apache Arrow**, enabling zero-copy hand-off to Arrow-aware consumers. Querying Arrow data with DuckDB is **10-100× faster than processing plain JS objects**. Practical guidance:\n- Keep results in Arrow as long as possible; convert to JS objects only for the small slice actually rendered.\n- For charts (echarts is in the stack), feed typed columnar arrays from Arrow vectors rather than arrays-of-objects — less GC churn on the main thread.\n\n**`apache-arrow` (JS)** — 11k+ stars, Apache-2.0, healthy (v21.x, 360+ contributors) — is the interop/type backbone. **`@uwdata/flechette`** is an optional lighter, zero-dependency Arrow reader/writer (~14kB gzip vs ~43kB; 2-11× faster extraction) and is what Arquero v8 now uses internally. Adopt flechette if renderer bundle size matters and you only need read/extract.\n\n---\n\n## 5. Big-CSV ingestion (the failure mode to avoid)\n\n**Anti-pattern:** reading a 200MB+ `File` into a JS string / ArrayBuffer, or pushing it through IPC. This blows main-thread memory and stalls the UI.\n\n**What the app does right:** `upload-to-duckdb.ts` is path-based — Electron passes a real path and DuckDB's **vectorized `read_csv`** streams off disk in the main process. Keep it. Make `AUTO_DETECT` use a bounded `SAMPLE_SIZE` (already parameterized as `sampleSize`) so type detection doesn't scan the whole file.\n\n**Browser-only fallback** (only if a non-Electron build ever exists): use OPFS + DuckDB-Wasm:\n```ts\nawait db.registerFileHandle('big.csv', opfsFileHandle, DuckDBDataProtocol.BROWSER_FSACCESS, true);\nawait conn.query(\"CREATE TABLE t AS SELECT * FROM read_csv('big.csv', AUTO_DETECT=true)\");\n```\nDuckDB-Wasm reads the OPFS file in **pages** rather than loading it whole — that's the only way to handle large files within the WASM memory limit.\n\n---\n\n## 6. duckdb-wasm tuning (only relevant for a browser-only fallback)\n\nIf you ever ship a pure-web build, these are the levers:\n\n### Three bundles, capability-gated\n- **MVP** — single-thread, maximum compatibility.\n- **EH** — adds WASM exception handling (faster, better errors).\n- **COI** — **multi-threaded** via SharedArrayBuffer + pthread workers + SIMD. **Requires Cross-Origin Isolation**: `COOP: same-origin` + `COEP: require-corp` response headers.\n\nUse `selectBundle()` for graceful fallback — it feature-detects and picks the best supported bundle:\n```ts\nconst bundle = await duckdb.selectBundle(duckdb.getJsDelivrBundles());\nconst worker = new Worker(bundle.mainWorker!); // ALWAYS in a worker — 3.5MB WASM\nconst db = new duckdb.AsyncDuckDB(logger, worker);\nawait db.instantiate(bundle.mainModule, bundle.pthreadWorker);\n```\n\n### Medium-end / no-WebGPU notes\n- WebGPU isn't used by DuckDB-Wasm anyway — it's **WASM-SIMD + (optionally) WASM threads**. So the \"WebGPU often unavailable\" constraint doesn't bite the engine; the real gate is **whether you can serve COOP/COEP headers** for the multi-thread bundle. In Electron you control headers, so COI is achievable; on a plain static host it may not be.\n- COOP/COEP **breaks cross-origin embeds without CORP** — but for an offline app loading only local assets, that's a non-issue. Set the headers (in Next.js via `headers()` / the custom server) and you get the threaded bundle.\n- **OPFS persistence** (`DuckDBOPFSConfig`, landed 2024-2025) survives reloads at near-native speed and beats IndexedDB for this. Use OPFS for the persistent DB file; never IndexedDB for analytical data.\n- **Always lazy-load** the 3.5MB WASM in a worker; never on first paint.\n\n---\n\n## 7. Web-worker offloading\n\n- **Native path:** DuckDB already runs in Electron main, so the heavy work is off the renderer thread by construction. Comlink is still useful to wrap **client-side Arquero transforms** in a renderer-side worker so a big pivot doesn't jank the UI.\n- **Comlink** (GoogleChromeLabs, ~11k stars, Apache-2.0, ~1.1kB) — already a dependency. Pattern:\n```ts\n// transforms.worker.ts\nimport * as Comlink from 'comlink';\nimport * as aq from 'arquero';\nComlink.expose({ pivot: (arrowBytes, spec) => /* aq.fromArrow(...).groupby(...).rollup(...) */ });\n// main\nconst api = Comlink.wrap(new Worker(new URL('./transforms.worker.ts', import.meta.url)));\nconst result = await api.pivot(Comlink.transfer(bytes, [bytes.buffer]), spec); // transferable, zero-copy\n```\nUse **Transferables** (Arrow byte buffers) so you move memory, not copy it.\n\n---\n\n## 8. Columnar transforms — Arquero vs SQL\n\nDecision rule:\n- **Stays in SQL** when the transform is expressible as group-by/window/join/aggregate over a registered dataset → let DuckDB do it (faster, out-of-core, no data egress to renderer).\n- **Use Arquero** when: data is already small in the renderer (a few k rows / a prior aggregate), you need quick interactive derive/pivot/reshape, and you want to avoid an IPC round-trip. Arquero (BSD-3, 1.5k stars, active May 2025, now on flechette) is the mature choice. Run it in a worker (§7) for anything non-trivial.\n- **Avoid** Arquero/Danfo for full-table multi-hundred-MB scans — that's where they lose 10-100× to DuckDB and risk main-thread OOM.\n\n---\n\n## 9. Risks / cleanups to land\n\n1. **Parameter binding (security + perf).** `runReadOnlyQuery` is SQL-only and `params` are cache-key only (documented TODO in `duckdb.ts`). Neo supports real prepared statements — add a bound-parameter API in the main-process service and route user-driven filters through it. Eliminates the string-concatenation injection surface and lets DuckDB cache plans.\n2. **Thread/memory caps.** Confirm the service sets `threads` and `memory_limit` (don't let a query grab all cores or all RAM on an 8GB machine). Set `temp_directory` so big joins spill instead of crashing.\n3. **Result-size guardrails.** Enforce server-side `LIMIT`/aggregation in `previewDataset`/`useTablePreview`; never let the renderer request a full multi-million-row table. Pair with table virtualization in the UI.\n4. **Arrow transfer for big results.** Where large result sets cross IPC, move to Arrow IPC chunks instead of JSON to cut serialization cost and main-thread GC.\n5. **Object cache.** Turn on `PRAGMA enable_object_cache` for repeated queries against the same cached Parquet files.\n\n---\n\n## 10.
